CASE 1

📜 claude.md: evolution in 4 real updates

Scenario

Lucas is a tech lead at a B2B SaaS logistics startup (TypeScript/Next.js + Supabase). Project has 6 devs. Started with Claude Code 2 months ago. Claude gets basic things wrong — uses a different enum, ignores naming convention, generates test with wrong mock. Lucas updates claude.md 1x a week.

❌ claude.md v1 (week 1) — "everything I think is important"

# Logix Project B2B freight management system. ## Stack - Next.js 14 (App Router) - Strict TypeScript - Supabase (Postgres) - Tailwind + shadcn/ui - Vercel deploy - Vitest ## Conventions - Components in PascalCase - Hooks on useXxx - Pastes in kebab-case - Absolute imports with @/ - Style: 2 spaces, no semicolons - Commits: conventional commits ## Structure - /app — App Router - /components — shared - /lib — utilities - /hooks — custom hooks - /db — schemas and migrations ## How to run npm install npm run dev ## Tests Vitest. Run with npm test. ## Deploy Push to main → Vercel deploy. [plus 130 lines with details of each module, examples of each hook, list of all database tables...]

Problems:

  • • 180 lines— inflated claude.md fires many tokens every session
  • • MIXES content “universal information” (stack) with “module-specific details”
  • • Don't say NEVER— just "conventions", as if they were suggestions
  • • Lack of guidance on repeated types of error from Claude (does not talk about mocks, enums, test forms)

🟡 v2 (week 2) — after 3 recurring errors

Claude usedDate.now()in 4 different places (codebase usesuseNow()custom hook). I mocked Supabase in different ways in each test. Added semicolons in 1 PR.

Lucas added "Rules" section:

## Rules (NEVER / ALWAYS) - NEVER use Date.now() or new Date(). ALWAYS useNow() from @/hooks/useNow - NEVER mock Supabase manually. ALWAYS mockSupabase() from @/test/utils - NEVER add semicolons. Prettier will complain. - NEVER create a new hook without the use* prefix - ALWAYS prefix issue/PR with module prefix (FREIGHT-, AUTH-, etc.)

Result:better, but claude.md already has 200 lines. And the 130 lines of "module details" are still there inflating context.

🟡 v3 (week 4) — extraction via @ for long details

Lucas realizes that 70% of claude.md is "info that Claude only needs when he touches that module". Create folder/docs/claude/and extract details:

~/logix/ ├── claude.md # 95 lines — essential only ├── docs/claude/ │ ├── auth.md # auth module details │ ├── freight.md # freight module details │ ├── db-schema.md # complete database schema │ ├── testing.md # detailed test patterns │ └── deploy.md # deploy pipeline ## in claude.md, references: - To work on auth, read @docs/claude/auth.md first - To change shipping, read @docs/claude/freight.md - For testing, complete standard at @docs/claude/testing.md

Result:claude.md in 95 lines. Claude reads @docs only when entering the corresponding module. Baseline tokens fell 65%.

✅ v4 (week 8) — the mature version

After 4 weeks of actual use, Lucas refined it. final claude.md has 87 lines. Structure that stopped changing:

# Logix — Claude Code instructions

## Who am I (and who are you dealing with)
Team of 6 senior devs. No juniors. Do not explain basic concepts.
Direct technical language, no preamble, no "great, I'll go now...".

## Stack (summary)
Next.js 14 App Router · Strict TS · ​​Supabase · Tailwind+shadcn · Vitest · Vercel
Details at @docs/claude/stack.md

## NEVER-EVER rules (updated as Claude gets it wrong)
- NEVER Date.now()/new Date() — ALWAYS useNow() from @/hooks/useNow
- NEVER mock Supabase manually — ALWAYS mockSupabase() from @/test/utils
- NEVER semicolon — Prettier complains
- NEVER create a file >500 lines — split into sub-files
- NEVER `any` in TS — if necessary, comment the reason on the top line
- NEVER push directly to main
- ALWAYS prefix PR (FREIGHT-, AUTH-, USERS-...)
- ALWAYS test the function you added (and the one you changed if it changed behavior)
- ALWAYS run npm run typecheck before asking for review

## Module map (read when entering each one)
- Auth → @docs/claude/auth.md
- Freight (core) → @docs/claude/freight.md
- Billing → @docs/claude/billing.md
- Schema DB → @docs/claude/db-schema.md
- Testing → @docs/claude/testing.md
- Deploy → @docs/claude/deploy.md

## PRs
Template at @docs/claude/pr-template.md
Mandatory standard: context, executed plan, files with reason, test evidence, risks.

## Expected workflow
1. Always plan mode before touching >3 files
2. Always use the "tests" sub-agent to run and analyze tests
3. Always subagent "code-reviewer" before I call you
4. You DON'T merge. I merge.

## When you make a mistake
If I tell you "update claude.md so you don't do X again", add the rule in the NEVER-EVER section — not in the stack or modules section.

🧠 How to evolve yours

Principle 1 — Separate essential from detail:claude.md has just what Claude needs in EVERY conversation. Details go to @docs/claude/.
Principle 2 — Rules > conventions:"NEVER/ALWAYS" is stronger than "we prefer/usual".
Principle 3 — Evolve by reacting to real error:Don't try to predict. Let Claude make a mistake. Add rule. Repeat.
Principle 4 — Limit size:≤100 lines is the sweet spot. Above that, extract.
Principle 5 — Versioning in git:claude.md is code. PR reviews may question the rule.

CASE 2

📋 Skipping Plan Mode cost a day (and almost the feature)

Scenario

Patrícia (PR Full+, 3 years) needs to implement a "customizable report export" feature — user chooses columns, filters, format (CSV/PDF/XLSX), saved as a template. Issue says "5 days estimated". Patrícia is confident: “it’s just another export feature”.

❌ No plan mode — Tuesday 9am

Patrícia opens Claude Code directly through the terminal:

"Implements the customizable report export feature from issue REPORT-142. Reads the ticket in Jira first."

Claude reads, takes action. Create componentCustomReportExporter, changes 7 files, adds endpoint, creates 3 hooks. Tests run, pass. PR opens at 5pm.

Tech lead review, morning after:

"Patricia, this new endpoint/api/reports/exportconflicts with the/api/v2/reports/exportwhich was already being designed in PR #882. Haven't you seen? We are migrating to v2 this month. And the CustomReportExporter became Frankenstein — it duplicates the logic of the ExportTrigger that already exists. We're going to have to redo it."

Cost of error:1 day lost. Patrícia needed a heavy rebase on PR #882, actually rewriting, redoing tests. Instead of the estimated 5 days, he spent 7.

✅ With plan mode — fourth restart

Patricia starts again. Open plan mode (Shift+Tab×2 + Opus Plan setting):

[Plan Mode • Opus] "Implements REPORT-142 (customizable export). FIRST presents me with a DETAILED plan: new files, files to change, endpoints, conflicts with open PRs, risks. Wait for my OK before touching any file."

Claude returns 8 minutes later:

REPORT-142 PLAN

Conflicts detected (I audited active branches):
- PR #882 (in progress) is drawing /api/v2/reports/export. YOUR feature MUST use v2, not create parallel v1.
- ExportTrigger already exists in /components/reports/ — extend instead of creating CustomReportExporter.
- Type ExportFormat already exists in /types/reports/. Do not create new enum.

NEW files (3):
- /components/reports/ReportColumnPicker.tsx
- /components/reports/ReportFilterBuilder.tsx
- /lib/reports/exportTemplate.ts (save/load template)

Files to CHANGE (4):
- /components/reports/ExportTrigger.tsx (add "custom" entry)
- /api/v2/reports/export/route.ts (add custom params — coordinate with PR #882)
- /db/migrations/2026_05_xx_report_templates.sql (new table)
- /types/reports/index.ts (extend ExportFormat, add ReportTemplate)

Risks:
1. PR #882 has not yet merged — I need to wait OR coordinate with Felipe (author) to work on chained branch
2. New migration requires DBA approval before applying to staging
3. Performance: will customization accept up to X columns and Y filters? No limit can generate slow queries

Estimated effort:4 days with PR #882 already merged. 6 days if you need to work in parallel coordinating.

Approve plan? Want to adjust before I start?

Patrícia coordinates with Felipe (15 min Slack), decides to wait for PR #882 to merge (it will be tomorrow), and starts on Thursday. Ends Saturday 2pm, no day lost. Tech lead approves PR without heavy refactoring.

🔀 Variations tested for plan mode

A — Small Feature (1-2 files):skips formal plan mode, but asks "tell me which files will play first". Mini version of the plan.
B — Wide refactor (10+ files):plan mode in 2 phases — first "maps everything that needs to change", then "groups it into logical commits".
C — Ambiguous bug (root cause unknown):plan mode is "first root cause hypothesis, probability ranking, investigation plan". Implementation only later.
D — Stack migration:Mandatory plan mode of 1 full page before any line. The cost of making mistakes here is extremely high.

⚠ Errors when using plan mode

  • • "I already know what to do, plan mode is overhead"— this is the thought that cost Patrícia 1 day. Plan mode on features >3 files is non-negotiable.
  • • Approve plan without reading it properly— if you didn't absorb it, ask Claude to summarize it in 5 bullets first.
  • • Do not audit conflicts with open PRs— explicitly ask for "audit active branches and list me conflicts".
  • • Forget Opus Plan setting— Opus plans, Sonnet executes. Cost of Sonnet, quality of Opus.

CASE 3

🌳 3 worktrees in parallel — real coordination

Scenario

Igor, senior dev. Monday 9am. List of the day: (1) "client tags" feature (4-6h), (2) timezone bug in weekly report (1-2h), (3) public API v2 documentation (2-3h). Estimated total 7-11am. Igor decides to run parallel.

✅ Setup of the 3 worktrees

# Terminal 1
cd ~/work/saas-main
claude-worktree feature-customer-tags
# open cd ~/work/.worktrees/feature-customer-tags

# Terminal 2 (another tab)
cd ~/work/saas-main
claude-worktree bug-timezone-weekly-report

# Terminal 3 (another tab)
cd ~/work/saas-main
claude-worktree docs-api-public-v2

Each one in its own branch, isolated working tree, separate context. Claude in each terminal doesn't see what the others are doing (they work on probably different files).

⏱ How the day went in practice

9:00 am:Igor starts T1 (tags). Plan mode + Opus Plan. Wait flat while assembling T2.
9:08 am:T1 flat ready. Igor approves, T1 starts executing. Go to T2 (timezone bug).
9:12 am:T2: "reproduce the bug first, without touching code. Use the test report in /fixtures/reports/2026-05-12.json."
9:25 am:T2 reproduced, identified that the formatWeek() function was not using the user's TZ. Ask for confirmation before fixing.
9:26 am:Igor (without leaving T2): "fix with context user's timezone. Adds test with 3 different timezones". Return to T3.
9:28 am:T3: "document API v2 endpoints in OpenAPI 3.1 format. Use the existing types in @/types/api/v2/. For each endpoint: description, req example, res example, possible error codes."
9:45 am:T2 finished (bug fixed + 3 tests passing). Igor reads code, approves, /commit-push-pr.
10:12 am:T1 (tags) comes back with a question: "is this existing_tags column in the customer table a uuid or JSONB array? I checked migration and it is text. Confirm before I change it." Igor checks DB, confirms it is JSONB. Updates T1.
11:30 am:T1 delivery. 8 files changed, 6 tests added. Igor reviews in 20 minutes. Minor tweaks, /commit-push-pr.
12:00:T3 complete OpenAPI doc delivery. Igor reviews quickly, adjusts 2 confusing examples. Open PR.
12:22 pm:3 PRs ready. Lunch.

🧠 What made parallel functional

1. Isolated worktrees in git:no file collisions. Each Claude has its own working tree.
2. /focus on each terminal:Igor didn't read step by step. He only intervened with questions.
3. Claude asks before touching something ambiguous:claude.md rule ("if schema seems inconsistent, ask first"). Saved T1.
4. Plan mode in T1 (largest):the smaller ones (T2 bug, T3 docs) didn't need it. Plan mode has a cost, use where you pay.
5. Slash /commit-push-pr saved context:Igor doesn't write commit message, he doesn't type gh pr create. 1 command.

⚠ When NOT to use 3 worktrees

  • • Same code area:If T1 and T2 move the same folders, merge conflict is certain. Sequential.
  • • You still drool over each one:If you don't trust /focus, parallel becomes chaos. Master 1 before moving up.
  • • For broad refactor (1 large):1 concentrated session is better than 3 with chunks.
  • • Sweet spot is 3-4:5+ becomes manual management. Bori Cherny says 5, but he is the creator. Start at 3.

🧠 The N4 standard of the 3 cases

  1. 1. claude.md evolves REACTING to error, not prediction. Each recurring error → 1 line of NEVER-EVER.
  2. 2. Plan mode on features >3 files is non-negotiable.The cost of 8 minutes of planning ≠ the cost of 1 day of refactoring.
  3. 3. Isolated worktrees + /focus + custom slash commands= you operate a team of 3-4 without becoming a nanny.
  4. 4. Claude MUST ask when something is ambiguous(inconsistent schema, uncertain context). Put this in claude.md.
  5. 5. You DON'T merge.Claude delivers PR. You review. You would merge. Explicit rule prevents accidents.
