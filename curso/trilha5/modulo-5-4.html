CASE 1

🤖 "PR review 24/7" routine in production for 90 days

Scenario

Carla is the CTO of a 14-dev B2C startup. Human code review becomes a bottleneck: PRs spend 8-24 hours waiting for the 1st review. Devs complain. Carla decides to set up a routine:every open PR receives automatic review in < 5min, with inline comments. Human still approves merge, but arrives in PR with 1st pass made.

❌ Naive version that ALMOST went into production

Carla's routine v0: "every GitHub event 'pull_request opened' → Claude reads complete diff + triggers comments directly in the PR".

The 4 latent problems:

  • • No token budget— Large PR (1k+ lines) could burn R$80 alone. Without a cap, costs explode.
  • • No rate limit— someone opens 5 PRs in 2 minutes, 5 simultaneous reviews.
  • • No distinction between human PR and bot/Dependabot PR— automatic review in Dependabot PR is an obvious waste of no value.
  • • Direct comment without approval— author sees Claude's "wrong" comment and loses confidence in the entire team.

✅ Production version (after 4 iterations)

Trigger:GitHub webhook on PR opened/synchronize.

Security hooks (non-negotiable):

# pre-routine-start hook - If the PR author is a bot (dependabot, renovate, snyk-bot): ABORT, log "skipped: bot author" - If diff > 2,000 lines: ABORT + post comment "PR too large for automatic review. Human reviewer will be notified." - If it contains a file in /db/migrations/, /infra/, /.github/workflows/: ABORT + post comment "Sensitive. Human review only." - If there is already a comment from "claude-reviewer" on this PR (sync trigger): runs in INCREMENTAL mode (only new diff since last review) # task-budget hook - Total cap: 30k tokens per run. Ends gracefully approaching the limit. - Monthly cap per repo: R$600. If exceeded, pause routine + CTO alert. # post-routine-end hook - Post comments in DRAFT mode (pending review) — not in APPROVE mode - Ping human reviewer designated to arbitrate comments - Always adds disclaimer: "Review generated by Claude. Human confirms."

Routine prompt:

You are a senior code reviewer at this startup. Read claude.md first to understand conventions. For this PR: 1. Evaluate whether the objective is clear in the description. If not, comment asking for context. 2. Read the entire diff carefully in: - Logic that can break in edge case - Violated standard from claude.md (cite exactly which one) - Missing test for change made - Naming inconsistent with convention - TODO forgotten, console.log forgotten, debug forgotten 3. For each problem, comment INLINE in the code with a concrete suggestion. Use [self] suffix. 4. Use GitHub's "suggested change" feature when applicable — human review can be accepted in 1 click. 5. Final summary as an overview of the PR (status: approve / request changes / comment-only). RULES: - DO NOT use a "robotic" tone. Direct, technical, human-like language. - DO NOT comment obvious ("add a test") without saying WHICH test. - DO NOT attack the author. Criticize the code. - ALWAYS state the reason for the suggestion. - If something is EXCELLENT, praise it in 1 line (motivates the author). - Limit 8 comments per PR. If you have more, choose the 8 most critical + 1 overview citing "other smaller points in the next pass".

CASE 2

🛡 The pre-tool-use hook that saved from a DROP TABLE

Scenario

Felicidata team (B2B dataops). Ricardo, dev, configured a routine for Claude to clean temporary tables from the warehouse weekly. I mistakenly pasted the name_users_temp_2026_05_wrong in config — the correct actual name of the production table isuserswithout underscore. The routine, executing autonomously, would runDROP TABLE usersin production.

✅ The hook that was there 6 months ago

Felicidata had a pre-tool-use hook that Ricardo didn't even remember setting up:

# /.claude/hooks/pre-tool-use/database-guards.js module.exports = function(tool, context) { if (tool.name !== 'sql_execute') return { allow: true }; const sql = tool.params.query.toUpperCase(); // ABSOLUTE BLOCKING without exception: if (sql.match(/\bDROP\s+TABLE\b/) || sql.match(/\bTRUNCATE\b/)) { if (!sql.includes('_TEMP_') && !sql.includes('_STAGING_')) { return { allow: false, reason: 'DROP/TRUNCATE detected in table without _TEMP_ or _STAGING_ suffix. Human approval required.', escalate_to: 'oncall@felicidata.io', require_token: true // requires Ricardo to enter manual token in the panel }; } } // BLOCKING in production without WHERE: if (sql.match(/^DELETE FROM/) && !sql.includes('WHERE')) { return { allow: false, reason: 'DELETE without WHERE in production.', escalate_to: 'oncall@felicidata.io' }; } // Other DROPs and DDLs: allow but LOG if (sql.match(/\b(DROP|ALTER|TRUNCATE)\b/)) { log({ type: 'sensitive_ddl', sql, agent: context.agent_id }); } return { allow: true }; };

When the routine ran and triedDROP TABLE users, the hook FIRED. Blocked. Sent an alert to oncall. Ricardo received Slack at 3:22 am (which he only saw in the morning): "BLOCKED: DROP TABLE users — requires human approval."

🧠 Post-mortem analysis

What failed in the config:Ricardo had typed a table name without the suffix_temp_expected. Simple human error — 4 characters missing.
WHAT SAVED:hook had explicit rule: "DROP without suffix _TEMP_/_STAGING_ = absolute blocking". It doesn't matter which table.
Principle:hooks don't trust human config. They operate as a network firewall — black list by default, white list by exception.
Avoided cost:recover from DROP TABLE users in production = hours of downtime, session loss, possible loss of data not covered by the last 4h backup. Internal estimate: R$80-180k.

🛡 Other hooks that would be useful in your setup

  • • pre-tool-use:blockrm -rfin non-whitelist path; blockgit push --forcein main; block command that sends external email without approval
  • • post-edit:run linter/formatter on every edited file; check if commit does not include secrets
  • • stop:notify Slack/email when long session ends; save automatic summary to /sessions/
  • • response:badge on the terminal when Claude needs human input (does not go unnoticed)

CASE 3

🚀 First SaaS product with Agent SDK — from provider to builder

Scenario

Helena, solo dev, has been selling implementation services for 3 years (R$ 8-15k/project). It sees 80% of customers asking for the SAME thing: importing a list of leads from LinkedIn, enriching it with public data (website, company LinkedIn, recent news), ranking by ICP fit, exporting to CSV ready for Outreach/Apollo. Helena thinks:"If it's the same thing every time, it's become a product."

The decision:use Agent SDK to package what it already does manually in a small SaaS. He doesn't want to compete with Apollo. It wants to serve the 200 accounts that require "a layer of intelligence" and pay R$200-500/month.

✅ "LeadFit" product MVP

Architecture:

  • • Simple frontend (Next.js) — CSV upload, dashboard, export
  • • Backend Node + Agent SDK (TypeScript) — agent orchestrator
  • • 3 specialized agents:
  • – Scraper:collects website/LinkedIn/news data (with 7d cache for the same company)
  • – ICPMatcher:evaluates fit based on the ICP rules that the customer registered
  • – Enricher:generates personalization note for each lead (4-5 lines to use in the email)
  • • Postgres + Redis for caching
  • • Stripe for billing

Essential hooks from day 1:

  • • Token budget per customer/month (rigid cap based on plan)
  • • Rate limit per agent (to avoid hitting the scraping API limits)
  • • Fallback if 1 agent fails (continues the others, marks lead as "enriched: partial")
  • • Idempotence (even CSV does not re-process)

⚠ Lessons from the beginner builder

  • • MVP needs to fit into 1 mental prompt.“Import lead → enrich → rank → export” is simple. Helena didn't try to become an "Apollo killer". Focus kills feature-creep.
  • • Token budget per plan is essential on day 1.Without this, the first "smart" client uploading a CSV of 5k lines will result in zero margin for the month.
  • • Transparent pricing on AI cost.Helena says "up to X leads/month included, R$Y per extra thousand" — customers understand, they don't fight.
  • • SDK doesn't get rid of UX.40% of Helena's time was in UX/onboarding. Agentic backend is "easy" compared to making the client use it right.
  • • Content > ads in the pre-PMF phase.Helena wrote 12 technical posts on Linkedin about lead enrichment. 64% of customers arrived from there.
STANDARD
★

🧠 Standard N5 of the 3 cases

  1. 1. Hooks DO NOT trust human config— operate as a firewall. White list by exception, not black list.
  2. 2. Token budget per execution AND per month— double cap. Without this, the cost explodes in 1 error.
  3. 3. Routine with clear pre/post hooks— before running, decide if you should. Then, audit. Full visibility.
  4. 4. Mode "draft" before "executor"— Claude posts suggestion, human confirms. For 4-8 weeks. Then you relax.
  5. 5. SaaS with Agent SDK starts with 1-sentence MVP— "imports X → enriches → exports Y". No feature creep in the first 6 months.
